# 우당탕 식탁대전

개인 사진을 붙인 3D 채소 피규어로 상대를 원형 식탁 밖으로 밀어내는 1인 대 로컬 NPC 게임입니다.
토마토와 고구마의 입체 몸체는 직접 만든 절차적 메시이고, 얼굴은 몸체 앞에 고정한 얕은 초상 면입니다.
강아지의 실제 3D 머리를 복원하는 기능은 아닙니다. 기존 카드의 그림·인쇄 이름·스탯·포일은
그대로 두며, 게임의 표시 이름과 물리 값은 별도입니다.

## 실행

새로 실행할 때는 저장소 루트에서 기존 미리보기 포트와 겹치지 않는 로컬 정적 서버를 실행합니다.

```powershell
python -m http.server 5177 --bind 127.0.0.1
```

[로컬 게임](http://127.0.0.1:5177/ringout.html)을 엽니다. 빌드·npm 설치·백엔드는 필요하지 않습니다.
`file://`는 ES 모듈과 이미지 처리의 실행 환경이 아닙니다. 다른 작업의 서버를 중지하지 않습니다.
도감의 게임 링크로 진입하거나 `ringout.html`을 직접 열 수 있습니다.

저장소를 상위 폴더에서 서빙하면 `http://127.0.0.1:포트/DAENGS_CARDS/ringout.html`처럼 서브경로로 열립니다.
그 구성에서도 상대 경로의 모듈·이미지가 `/DAENGS_CARDS/` 아래로 해석되는지 확인했으며, 기록은 아래 검증 표에 있습니다.

## 조작과 규칙

1. 바로 네오로 시작하거나 사진과 표시 이름을 바꿉니다. 얼굴 미리보기에서 위치와 확대를 조정하고 확정합니다.
2. 자신의 몸체와 연습 상대의 몸체를 고릅니다. 토마토끼리·고구마끼리 대결도 가능합니다.
3. 내 피규어에서 발사 방향의 반대쪽으로 끌었다 놓습니다. 바닥 화살표와 게이지가 방향·힘을 보여 줍니다.
   짧은 드래그는 취소되고 최대 힘은 제한되며, 드래그 중 들어온 두 번째 포인터는 무시합니다. 한 발을 쏘면 두 피규어가 멈추거나 떨어질 때까지 다음 입력이 잠깁니다.
4. 둘 다 식탁에 남으면 NPC와 번갈아 쏩니다. 피규어의 **바닥 중심**이 원형 플랫폼의 바깥 경계를 넘으면 탈락합니다.
   탈락한 피규어는 지면 충돌에서 빠지고 낙하합니다. 몸통 일부가 가장자리에 걸치는 것만으로 탈락하지 않습니다.
5. 한 발 전체가 끝난 후 상대만 탈락하면 승리, 나만 탈락하면 패배, 둘 다 탈락하면 무승부입니다.
   최대 20개의 개별 발사까지 진행하고, 마지막 발의 탈락을 먼저 판정한 뒤 둘 다 남으면 턴 제한 무승부입니다.

경기장에 키보드 초점을 두면 **←/→는 방향을 5도, ↑/↓는 힘을 5%씩** 조절하고
**Space/Enter로 발사**, **Esc로 일시정지/계속하기**합니다. 같은 조작을 화면의 방향·힘 슬라이더와
발사 버튼으로도 할 수 있습니다. 이름 입력 등 일반 폼에서는 게임 단축키를 가로채지 않습니다.
일시정지·계속하기·소리·다시 하기·선택으로 돌아가기를 제공합니다. 소리는 기본 꺼짐이며 버튼을 누른
뒤 브라우저에서 합성합니다. 외부 음원 파일은 추가하지 않았습니다.
다른 탭으로 이동하면 자동 일시정지하며 돌아온 뒤 명시적으로 계속해야 합니다.
45–90초는 플레이테스트 목표이며 보장 시간이 아닙니다.

## 코드 경계

| 책임 | 데이터·동작 |
| --- | --- |
| 프로필·사진 준비 (`ringout-profile.mjs`, `ringout-photo.mjs`) | 로컬 프로필 ID, 표시 이름, 얼굴 리비전, 처리된 얼굴 Blob 및 로컬 기록. 업로드 원본은 메모리에만 유지 |
| 몸체 정의 (`ringout-data.mjs`) | 몸체 ID별 질량·최대 충격량·마찰·충돌 반지름·시각 크기. 카드 스탯과 무관 |
| 경기 시뮬레이션 (`ringout-engine.mjs`) | 고정 시간 간격의 평면 위치·속도·원 충돌·턴·탈락·결과. Three.js와 DOM을 참조하지 않음 |
| 3D 렌더러 (`ringout-renderer.mjs`) | 몸체별 얼굴 fit, 시뮬레이션 위치를 메시로 표현. 얼굴 재질은 각 액터별로 독립. 흔들림·낙하·승리 포즈는 표현 |
| UI·수명 관리 (`ringout-ui.mjs`) | 화면 입력을 바닥 좌표로 변환, 프로필과 선택 연결, 시작·취소·재도전·일시정지, 결과를 한 번만 기록 |

프로필 교체·삭제·경기 재시작·선택 복귀는 경기 인스턴스와 세대 번호로 이전 작업을 무효화합니다.
고정 시간 간격의 누적기는 **활성 시간**만 받고, 탭이 숨겨진 시간을 복귀 때 몰아서 처리하지 않습니다.
충돌은 최대 속도에서 이동량이 제한되는 작은 스텝으로 계산합니다. NPC도 같은 발사 API와 힘 제한을 쓰며
시드 기반의 제한된 오차를 사용합니다. 미래의 플레이어 입력을 읽거나 피규어를 순간 이동하지 않습니다.

Three.js **0.180.0**을 로컬에 고정해 상대 경로 ES 모듈로 사용합니다. 필요한 모듈도 같은 릴리스로 맞추며
외부 런타임 CDN에 의존하지 않습니다. 공식 설치 문서는 빌드 없이 쓰는 경로와 의존 모듈 버전 일치를
설명합니다. 이 저장소에서는 이를 기존 정적 호스팅에 맞춰 로컬 vendoring으로 적용합니다.
([Three.js 설치 문서](https://threejs.org/manual/en/installation.html))

텍스처는 프레임마다 만들지 않습니다. 같은 몸체 구성에서는 확정한 얼굴 리비전이 바뀔 때만 갱신하고,
몸체 구성이 바뀌면 이전 텍스처를 해제한 뒤 같은 처리 얼굴 canvas로 다시 만듭니다(사진 재처리·재저장 없음). 사진의 색 공간과 알파를
유지하고 더 쓰지 않는 GPU 텍스처는 `dispose()`로 해제합니다. 액터가 같은 몸체여도 플레이어 사진을
NPC 재질에 공유하지 않습니다. ([Three.js Texture 문서](https://threejs.org/docs/pages/Texture.html))
라이선스와 정확한 배포 출처는 vendored 폴더에 함께 둡니다. Three.js의 MIT 라이선스는
재배포본에 저작권·허가 고지를 유지하도록 요구합니다.
([업스트림 라이선스](https://github.com/mrdoob/three.js/blob/dev/LICENSE))

### 표현과 렌더링 예산

사용자가 제공한 따뜻한 식탁 참고 이미지에 맞춰 토마토의 굴곡·잎 줄기·작은 토마토 장갑과 발,
고구마의 휜 몸체·보라색 껍질·뿌리 손가락을 절차적으로 제작했습니다. 사진 창에는 각 몸체 색의
얇은 입체 테두리를 두고, 무대는 민트색 원형 받침과 나뭇결 식탁·화분·머그·창가로 구성합니다.
표면 질감은 원본 canvas 노이즈·선으로 만들며 참고 이미지를 텍스처로 복사하거나 새 AI 이미지
API를 호출하지 않습니다. 참고 이미지는 아트 방향이며 같은 영화 수준의 렌더링을 보장하지 않습니다.

몸체 템플릿과 질감·기하 구조는 재사용하고 사진·가변 재질은 액터별로 분리합니다. 질감 canvas는
토마토·고구마·잎·받침 각각 256×256, 나뭇결 512×512, 접촉 그림자 128×128이며 초기화 때만
생성합니다. 렌더 픽셀 비율은 최대 1.6, 그림자 맵은 1024×1024 한 개입니다. 무거운 후처리는
사용하지 않습니다. 반복 선택·재경기에서 불필요한 geometry/사진 텍스처가 늘지 않게 캐시하고
종료 때 얼굴·화살표·그림자·렌더러 자원을 해제합니다.

선택 화면은 가까운 카메라와 1.3배 피규어를 사용하며, 경기에 진입하면 전체 바깥 경계를 포함하는
고정된 높은 카메라로 바뀝니다. 몸체의 실제 경기 크기는 `BODY_DEFS.visualScale`을 따릅니다.
화면 비율 0.65/0.84/1/1.5/2에서 경계 360점을 투영했을 때 최대 절대 NDC는 0.863 미만으로
모두 화면 안에 들어왔습니다. 이 기하 확인은 실제 모바일 성능 검증을 대신하지 않습니다.
WebGL 초기화/유실 때 안내와 다시 시도·도감 복귀를 제공하며, 대체 평면 화면을 3D 구현으로 표시하지 않습니다.
3D 초기화 이후의 그림·저장 정보 로드 실패는 WebGL 오류와 다른 문구로 구분합니다.

## 몸체와 물리 값

토마토는 가볍고 멀리 미끄러져 지나치기 쉽고 밀려나기 쉽습니다. 고구마는 무겁고 짧게 이동해
접촉 때 밀어내는 느낌이 크지만 먼 상대에 닿기 어렵습니다. 값의 정본은 몸체 ID 기반 데이터이며
표시 이름·카드 스탯·희귀도를 읽어 강도를 정하지 않습니다.

최종 구현 상수는 다음과 같습니다. 거리 단위는 월드 단위, 질량은 상대값이며
`발사 속도 = 힘(0–1) × 최대 충격량 / 질량`입니다. 마찰은 초당 일정한 속도 감소량입니다.

| 몸체 ID | 질량 | 최대 충격량 | 마찰(단위/s²) | 충돌 반지름 | visualScale |
| --- | ---: | ---: | ---: | ---: | ---: |
| `tomato` | 1.00 | 4.80 | 1.10 | 0.70 | 1.00 |
| `sweet-potato` | 1.35 | 5.30 | 1.50 | 0.64 | 1.00 |

| 공통 상수 | 값과 의미 |
| --- | --- |
| 플랫폼 반지름 | 4.2. 중심 좌표의 거리 **> 4.2**이면 탈락; 보이는 가장자리도 같은 값 사용 |
| 충돌 반발 계수 | 0.65, 겹침은 역질량 비율로 분리 |
| 고정 시간 간격 | 1/120초. 프레임당 받아들이는 시간 최대 0.25초, 최대 30스텝 |
| 정지 속도·유지 | 속도 ≤ 0.055에서 0으로 만들고, 모두 정지한 상태 0.16초 확인 |
| 안전 종료 | 한 발 9초에서 남은 지면 속도를 멈춤. 이미 시작한 낙하는 끝까지 확인 |
| 낙하 애니메이션 | 0.8초. 탈락 즉시 지면 충돌에서 제외 |
| 최소 발사 힘 | 0.035. 그 미만은 취소; 모든 입력의 힘은 최대 1로 제한 |
| 경기 한도 | 20개 개별 발사. 마지막 발의 탈락 결과를 먼저 판정 |

한 번의 합법 발사 후 고정 스텝당 이동은 충돌체 지름보다 충분히 작으며, 이동 전후의 경계 및
충돌 분리 후 경계를 검사합니다. NPC는 현재 거리·상대 질량을 참고해 같은 `shoot()`를 호출합니다.
방향 오차는 기본 ±0.37 rad에 확률 22%로 ±0.3 rad를 더하고, 힘 오차는 ±0.13이며 최종 힘은
0.3–1 범위입니다. 시드를 고정하면 오차도 재현됩니다. 현재 UI는 매 경기 같은 시드(`0x7392`)를 넘기므로 NPC 오차의
순서가 경기마다 반복됩니다. 경기별 시드 변화는 밸런스 플레이테스트와 함께 조정할 항목입니다.

몸체 추가는 해당 ID의 데이터, 절차적 몸체 제작 함수, 얼굴 fit을 추가하는 범위입니다.
양배추는 균형 잡힌 빠른 정지형, 과일 카드는 새 몸체 정의의 후보입니다. 미사용 캐릭터나 범용 플러그인
프레임워크는 만들지 않습니다. 식탁 축소도 이후 규칙 검토 항목입니다.

## 얼굴 준비와 재사용

JPEG·PNG·WebP를 브라우저에서 디코딩하고, 사용자가 원형 초상 창에서 사진을 옮기거나
0.5–6배로 축소·확대해 맞춥니다(편집 모듈은 타원형도 지원). 중앙 맞춤은 초기 제안일 뿐입니다.
귀·주둥이·털이 잘리는 경우 직접 조정합니다. 축소하면 귀를 위한 투명 여백을 남길 수 있습니다.
투명 원본의 알파는 유지합니다. **초상 창에 맞추는 기능이며 자동 배경 제거가 아닙니다.**
파일은 최대 12 MiB, 디코딩 결과는 최대 5천만 화소를 허용합니다. 파일 형식과 헤더를 확인하고
디코딩 오류를 안내합니다. `createImageBitmap`의 `from-image`로 EXIF 방향을 적용하며 지원되지
않으면 HTML 이미지로 디코딩합니다. 화소 상한은 디코딩 이후 확인하므로 큰 사진의 초기 디코딩
메모리까지 512×512로 제한하는 것은 아닙니다.
원본 전체 사진 대신 512×512 PNG의 처리된 얼굴 텍스처만 저장하고 재사용합니다.
몸체를 바꾸거나 다시 경기한다고 사진을 다시 처리·생성·저장하지 않습니다.

`art/tomato-subject.webp`와 `art/sweet-potato-subject.webp`는 얼굴 전용 파일이나 3D 모델이 아닌
완성 캐릭터 누끼입니다. 기본 네오의 얼굴은 승인된 저장소 아트에서 런타임에 잘라 사용합니다.
완성 카드 전체나 전신 누끼를 얼굴 면에 붙이지 않습니다.

기본 네오는 `art/tomato-subject.webp`(1279×1214)에서 측정한
`x=436, y=350, width=435, height=435` 영역을 원형으로 잘라 512×512 캔버스에 그립니다.
기존 이미지에서 준비하므로 사용자별 AI 생성이 없습니다.
사용자 제공 사진 8장의 실제 인코딩 크기는 아래 사진 검증 표에 기록했습니다.
얼굴 Blob의 크기는 사진과 인코더에 따라 달라지며 고정 바이트 수를 약속하지 않습니다.

얼굴 부착값은 `ringout-renderer.mjs`의 `FACE_FIT`에 있습니다. 가로·세로는 초상 면의
반지름이며, 위치는 몸체 로컬 좌표, 기울기는 X축 rad입니다. 같은 처리 얼굴을 이 부착값으로만
달리 표시하므로 몸체 전환에서 다시 crop하지 않습니다.

| 몸체 | 위치 x / y / z | 가로 / 세로 반지름 | 기울기 |
| --- | --- | --- | ---: |
| 토마토 | 0 / 0.87 / 0.65 | 0.435 / 0.445 | -0.19 |
| 고구마 | -0.025 / 0.99 / 0.56 | 0.365 / 0.485 | -0.18 |

## 이 기기에만 저장되는 프로필

IndexedDB의 `daengs-ringout` 데이터베이스, `profiles` 저장소, `active` 키에 활성 프로필 한 개를
저장합니다. 스키마 버전은 1입니다. 안정적인 로컬 프로필 ID와 얼굴 리비전을 두고
처리된 얼굴·표시 이름·몸체별 승수를 연결합니다. 몸체 선택은 프로필과 별도이며 얼굴 레코드를 복제하지 않습니다.
사진 교체는 자신의 프로필만 갱신하고 NPC는 독립된 데모 초상을 유지합니다.
이름은 제어 문자를 제거한 최대 24 Unicode code point이며 비어 있으면 `네오`입니다.
얼굴 교체는 ID를 유지하며 `faceRevision`을 올립니다.
프로필 ID와 경기 ID는 `crypto.randomUUID`가 없는 비보안 컨텍스트(LAN IP 접속)에서도 로컬 대체 ID로 동작합니다. 처리 얼굴 Blob은 PNG/WebP 최대 4 MiB를
허용하고 `faceBytes`에 실제 `blob.size`를 기록합니다. 사진 삭제는 슬롯을 새 ID의 기본 프로필로
교체해 이전 얼굴·승수·중복 지급 방지 기록을 제거합니다. `localStorage`에 대용량 이미지 데이터를 넣지 않습니다.
저장할 수 없으면 현재 세션에서 플레이하고 변경이 이번 접속에만 적용되며 이전 저장본이 남아 있을
수 있다는 안내를 보여 줍니다. 저장 실패 상태의 삭제를 디스크 삭제 성공으로 표현하지 않습니다.

같은 프로필의 몸체별 3승에서 작은 입장/받침 색 장식을 엽니다. 물리는 바뀌지 않으며
완료된 경기 결과를 중복 처리하거나 다른 프로필의 승수에 더하지 않습니다. 계정·서버 검증 기록은 아닙니다.
저장 쓰기를 순서대로 처리하고 편집/삭제 이후 완료된 옛 로드·디코딩·인코딩 결과는 무시합니다.
crop을 움직인 뒤 늦게 끝난 이전 인코딩도 다시 확인해야 합니다. 원본 사진은 메모리에만 두고
사용 종료 시 ImageBitmap과 object URL을 해제합니다. 업로드 사진·처리된 얼굴은 공개 저장소,
원격 로그, 외부 사진/AI 서비스로 보내지 않습니다.

페이지 CSP는 `connect-src 'none'`, `img-src 'self' blob: data:`, `form-action 'none'`을
지정해 원격 API 연결·이미지 목적지·폼 전송을 제한합니다. 모듈과 데모 아트는 상대 경로의 정적
요청이며 사용자 사진은 로컬 Blob/canvas입니다. 실제 브라우저 네트워크 검증은 아래에 따로 기록합니다.

### 이후 앱 연동 경계

현재 프로토타입에는 로그인·소유권 API가 없습니다. 이후 인증된 프로필 공급자를 붙일 경우
`userId`, `petId`, `displayName`, 접근이 허가된 얼굴 자산과 그 리비전을 받아 현재 로컬 프로필 경계에

  UI에서 1200×900 또는 390×844를 선택합니다. 합성 포인터의 capture만 검사 동안 대체하므로
  실제 드래그/capture 검사는 별도로 수행해야 합니다. 실행 중 탭을 보이게 유지합니다.

저장소 테스트와 별도로 같은 초기 배치에서 총 1,000경기(대진당 250)를 탐색 실행했습니다.
플레이어 역할의 스크립트는 현재 상대 방향에 ±0.22 rad 오차, 75–100% 힘을 사용했고 NPC는
게임의 규칙을 그대로 사용했습니다. 다음 시간은 사고·조작·UI 대기 시간을 제외한 시뮬레이션 활성 시간입니다.

경기 목표는 확인되지 않았습니다.** 입력을 실제 사람이 판단하는 플레이테스트로 추가 조정해야 합니다.
